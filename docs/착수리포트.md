# 아트그래프 착수 리포트

**Project Kickoff Report**

미술품·경매·미술관 소장품·갤러리·컬렉터 정보를 하나로 잇는 종합 포털 — 사전 조사부터 자동 갱신형 LLM 위키 아키텍처까지, 착수 전 논의를 정리한다.

- **Date**: 2026-08-27
- **Stage**: 착수 준비
- **Scope**: 아키텍처 설계 · 사전 세팅

---

## 01 · Mission — 왜 이 프로젝트인가

미술품, 경매, 미술관 소장품, 갤러리, 컬렉터 — 다섯 축의 정보를 한 곳에서 검색·질의할 수 있는 종합 포털을 만든다. 목표는 단순 검색창이 아니라, **자연어로 질문하면 근거를 인용해 답하는 LLM 위키**다.

> **Working thesis**
> 기존 서비스는 "DB + 검색 UI"에서 멈춰 있다. 이 프로젝트는 여기에 작품-경매-소장이력-컬렉터를 잇는 관계망과 자연어 질의응답 두 겹을 더한다.

## 02 · Landscape — 기존 서비스는 어디까지 하고 있나

해외는 경매가·시장 데이터 축적이 깊고, 국내는 경매사별로 파편화되어 있다. 두 축 모두 **미술관 소장·기증 이력**과 **컬렉터 프로버넌스**를 다루지 않으며, 자연어 질의 인터페이스를 갖춘 곳은 없다.

| 서비스 | 커버리지 | 비고 |
|---|---|---|
| Artnet | 경매 결과 1,800만 건 (1985~) | 유료 · ToS 크롤링 금지 |
| Artprice | 경매가·지수 데이터 (1962~) | 유료 · ToS 크롤링 금지 |
| Artsy | 경매 결과 + 갤러리·작가 정보 | 무료 열람 가능 |
| MutualArt | 작가 90만 명, 경매+전시 이력 | 가장 근접한 통합 구조 |
| 서울옥션 · K-Auction 등 | 자사 경매 매물·낙찰 정보 | 통합 검색 없음, 개별 운영 |
| 국공립 미술관 소장품 DB | 기관별 개별 운영 | 공공데이터 개방 일부 |

## 03 · Architecture — 3단 파이프라인: 수집 → 정규화 → LLM 위키

LLM을 매번 재학습시키지 않는다. LLM은 고정하고, LLM이 참조하는 **자료실만 매일 갱신**하는 RAG(Retrieval-Augmented Generation) 구조를 택한다.

```
[ 원본 수집 ]              [ 정규화 DB ]              [ LLM 위키 ]
 크롤러 · 공공데이터API      작가·작품·경매·미술관        문서화 + 임베딩
 JSON / CSV 원본 보존   →   갤러리·컬렉터 (관계형)   →   근거 인용 질의응답
                                                              │
        ▲──────────────── 매일 자동 · 변경분만 재반영 (diff) ──┘
```

사람이 매일 새 책을 꽂고, LLM은 질문받을 때마다 최신 책장을 뒤져 답한다 — 도서관·사서 비유가 곧 이 구조다.

## 04 · Data Ethics — 수집 원칙

- **공공데이터 우선** — 국공립 미술관 소장품, data.go.kr 개방 데이터부터 사용
- **사이트별 robots.txt / 이용약관 확인** — 대상 목록 확정 시 사이트별로 개별 검토
- **페이월 DB 제외** — Artnet · Artprice 등은 크롤링 대상에서 제외, 필요 시 정식 라이선스 검토
- **원본 보존** — 파싱 전 원본을 그대로 저장해 재처리 가능하게 유지

## 05 · Human Layer — 옵시디언의 위치

옵시디언은 자동화 엔진이 아니라 **같은 폴더를 여는 사람용 창구**다. 파이프라인이 매일 갱신하는 마크다운 볼트를 그대로 열어, 관계 그래프로 QA하고 오류를 주석으로 정정하는 검수 레이어로 둔다.

> **Role split**
> 자동화 파이프라인 = 데이터를 채우는 엔진 · 옵시디언 = 사람이 보고 검증하는 창구. 같은 git 저장소, 같은 폴더를 공유한다.

## 06 · Budget — 착수 전 필요한 계정 · 과금

Claude Code Pro · Gemini Pro는 대화형 구독이라 무인 자동화에는 적용되지 않는다. 매일 혼자 도는 파이프라인은 별도 종량제 API가 필요하다.

| 항목 | 용도 | 예상 비용 |
|---|---|---|
| Anthropic API 키 | RAG 질의응답 (Claude Haiku 4.5) | ₩3,000~5,000 / 월 |
| 임베딩 API | 문서 → 벡터 변환 (Gemini 임베딩) | ₩1,000 내외 / 월 |
| Supabase 무료 티어 | 정규화 DB + 벡터 검색(pgvector) | ₩0 (무료 티어) |
| GitHub Actions 무료 티어 | 매일 크롤러 자동 실행 | ₩0 (무료 티어) |

초기 규모 기준 **월 1만 원 안팎**으로 시작 가능. 트래픽이 붙기 전까지는 무료 티어가 대부분을 흡수한다.

## 07 · Checklist — 착수 전 준비물

- [ ] **Anthropic API 키 발급 + 소액 충전** — console.anthropic.com, 종량제 결제수단 등록
- [ ] **Supabase 무료 프로젝트 생성** — Postgres + pgvector, DB·벡터DB 겸용
- [ ] **GitHub 저장소 생성** — 크롤러 코드 + 마크다운 볼트 = 같은 저장소
- [ ] **옵시디언 설치** — 위 저장소 폴더를 볼트로 지정
- [ ] **1차 크롤링 대상 사이트 확정** — 공공데이터 우선, robots.txt/ToS 개별 확인

## 08 · Roadmap — 실행 단계

1. **대상 사이트 선정 · 크롤링 가능성 검토**
   공공데이터·미술관 API 우선 확인, 경매사 사이트별 robots.txt/ToS 점검
   → 사이트별 수집 가능 여부 표

2. **DB 스키마 설계**
   작가·작품·경매·미술관·갤러리·컬렉터 엔티티와 관계(외래키) 정의
   → Supabase 테이블 구조

3. **크롤러 개발 + 초기 적재**
   1차 대상 사이트부터 원본 수집 → 정규화 DB 반영 (1회성 초기 백필)
   → 초기 데이터셋

4. **마크다운 문서화 + 옵시디언 연동**
   DB → 작품/작가 단위 마크다운 자동 생성, 옵시디언 볼트로 지정
   → 위키 형태 1차 볼트

5. **임베딩 · 벡터 검색 구축**
   생성된 문서를 임베딩해 pgvector에 적재, 검색 레이어 구성
   → RAG 검색 레이어

6. **LLM 질의응답 연결**
   검색 결과를 근거로 Claude Haiku 4.5가 인용하며 답하는 인터페이스 구축
   → 질의응답 프로토타입

7. **자동 갱신 파이프라인 적용**
   GitHub Actions 스케줄러 + 변경분 감지(diff)로 매일 무인 갱신
   → 매일 자동 반영

8. **QA · 상시 운영**
   옵시디언에서 관계망 육안 검수, 오류 주석 → 정식 운영 전환
   → 운영 체계 확립
