직접 메시지로 지시. 승인 필요 항목(§2) 기준은 그대로 유지 — 메인이 대신
승인해줄 수 있는 게 아니라 여전히 사용자 승인이 필요함.

## 0. 전제 — 이 문서만으로는 세션이 안 깨어난다

이 문서는 "깨어났을 때 뭘 할지"의 기준이지, "깨우는" 장치가 아니다. 각 세션이
실제로 사용자 없이 계속 도는 건 Claude Code의 자율 루프(`/loop` 동적 모드,
`ScheduleWakeup`)가 그 세션에서 켜져 있을 때만 작동한다. 세 세션 각각 `/loop`가
켜져 있는지 세션 시작 시 확인할 것 — 안 켜져 있으면 이 문서를 따를 기회 자체가
없다.

## 1. 핵심 원칙

1. **유휴 금지(No Idle)**: 크롤링/DB 적재/정확도 검증 중 최소 하나는 항상
   백그라운드에서 돌고 있어야 한다. 하나가 끝나면 사용자 승인을 기다리지 말고
   즉시 아래 "3. 작업 큐"에서 다음 항목을 집어 시작한다.
2. **우선순위**: (a) 이미 진행 중이던 작업 완료·검증 > (b) 자기 레인의 작업
   큐(§3) > (c) 정확도/정합성 감사 재실행(멱등이라 언제든 안전 — 예:
   `audit_collectors.py`) > (d) 새 소스 발굴(리서치 필요, 우선순위 가장 낮음).
3. **기록이 유일한 교신 수단**: 사용자가 없을 때 세 세션이 서로 아는 유일한
   방법은 공유 문서뿐이다. 마일스톤마다(스크립트 완료, 대량 신규 소스 확보,
   버그 발견/수정, 소스 제외 결정) 그 즉시 해당 문서에 기록한다 — 나중에
   몰아서 쓰지 않는다.
   - 수집 현황 → `docs/크롤러현황.md`
   - 정확도/정합성 작업 → `docs/정합성작업.md`
   - 이 기준 자체에 대한 수정 제안 → 이 파일에 직접 추가
4. **체크인 주기**: 10~20분마다 (a) 자기 작업 진행 확인 (b) 다른 두 세션의
   문서/로그가 최근에 움직였는지 확인. 한 세션이 두 번 연속 체크에서 안 움직인
   것처럼 보이면 문서에 남기고, 가능하면 프로세스 생존 여부까지 확인
   (`ps aux`류) — 로그 갱신 간격이 커서 멈춘 것처럼 보이는 것과 실제로 죽은
   프로세스는 구분해야 한다.
5. **막히면 우회, 멈추지 않음**: 특정 소스가 robots.txt/ToS/429/스키마 문제로
   막히면 원인을 문서에 남기고(재조사 방지) 즉시 큐의 다음 항목으로 넘어간다.
   막힌 이유를 사람이 판단해야 하는 애매한 경우(§4)만 예외.

## 2. 자율적으로 해도 되는 것 vs 사용자를 기다려야 하는 것

**자율적으로 진행 가능** (이 문서의 취지 자체가 이걸 승인하는 것):
- 신규 크롤러 작성/실행, 이미 승인된 소스의 확장 수집
- 이미 검증된 로더로 DB 적재 (`pipeline/run.py --site <신규아님>`)
- 감사/리포트 스크립트 실행, 안전하다고 판단되는 자동 병합(동일 판정 근거가
  이미 문서에 선례로 남아있는 경우 — 예: 순수 유니코드 정규화 차이 병합)
- 진행 상황 문서화

**사용자 승인 필요 (자율 루프 중에도 예외 없이 대기)**:
- `truncate`/대량 `delete`, 스키마 변경(`ALTER TABLE` 등), 강제 재적재로 기존
  데이터 덮어쓰기
- 동명이인 위험이 있는 이름 병합(표기 순서/악센트/하이픈 차이 등 — 사람 확인
  필요하다고 이미 판단된 케이스)
- 유료/키 발급이 필요한 API, 법적 판단이 필요한 robots.txt 애매 케이스
  (`crawlers.txt` 없음, 명시적 허용/차단 신호 부재)
- git push, 외부로 나가는 요청(사용자 이메일/자격증명 포함 등)
- 원인 불명 실패가 반복될 때(같은 에러로 3회 이상 재시도 실패) — 무한 재시도
  대신 문서에 남기고 다음 큐 항목으로 넘어가되, 사용자에게도 남겨둘 것

## 4-0. Rembrandt 검색 랭킹 결함 — 근본 원인 정정 (2026-09-04)

§4-1에 기록한 `compact_for_embedding()`(표 압축) 수정은 **가설이 틀렸음이
소규모 검증으로 확인됨**: 표를 완전히 제거해도 진짜 Rembrandt van Rijn이
여전히 철자변형 "Rembrandt van Rhijn"(소장 1건)에게 밀림(0.9065 vs 0.9142).
**진짜 원인**: `intfloat/multilingual-e5-small`(384차원 소형 모델)이
"Rembrandt van Rijn"과 "Rembrandt van Rhijn"처럼 극도로 유사한 고유명사
표기를 의미적으로 구분할 해상도가 없음 — 코사인 유사도가 0.90~0.91대에서
사실상 동률로 나옴. **이건 임베딩 텍스트를 아무리 다듬어도 해결 안 되는
문제**(표 압축 자체는 나쁘지 않은 개선이라 유지하되, 단독으로는 불충분).

**시도한 해법**: 임베딩과 무관하게 쿼리 시점에 재정렬 — `query_vault.py`에
`rerank_by_richness()` 추가. 코사인 top-k를 `--top`의 6배 뽑은 뒤, 각 문서의
"(N건)" 표기 총합(소장작+경매기록 등 연결 데이터 양)에 `0.004 * log1p(count)`
가중치를 얹어 재정렬. **좁힌 5개 Rembrandt 변형 샘플로는 성공**(진짜 Rembrandt
0.9385 1위 vs 차점 0.9186)했지만, **실제 전체 코퍼스(23만 건)로 재실행하니
실패** — 진짜 Rembrandt van Rijn이 top5는커녕 후보 풀(top5×6=30개)에도
안 들어감. 원인: 후보 풀을 "원본 코사인 유사도"로만 먼저 좁히는 구조라,
23만 건 전체 중 "미술관"/"경매" 등 쿼리 단어와 우연히 잘 맞는 무관한 문서가
많아 진짜 Rembrandt가 그 30등 안에도 못 든 것으로 추정(전수 확인은 안 함).

**미해결 — 다음 세션 인계**: 두 가지 접근(임베딩 텍스트 다듬기, 좁은 후보군
재정렬) 모두 오늘 안에 실패로 끝남. 근본적으로는 (a) 후보 풀을 훨씬 넓히거나
(top 30 대신 top 200~500), (b) richness 점수를 매 쿼리마다 파일 읽어 계산하지
말고 `vault_embeddings`에 컬럼으로 미리 저장해 전체 코퍼스 스코어링을
numpy로 한 번에 처리하는 방향이 유력해 보이나 **검증 안 됨** — 다음 세션은
반드시 §4-1 체크리스트대로 작은 샘플이 아니라 **전체 코퍼스로** 먼저
검증할 것(오늘 실패 원인이 정확히 "좁은 샘플에서만 검증하고 전체로는
확인 안 함"이었음).

**사고 경위**: LLM Q&A 스모크 테스트로 "소장작 2,935건인 진짜 Rembrandt van Rijn이
소장 1건짜리 철자변형 중복에게 검색 순위를 뺏긴다"는 결함을 발견 → `embed_vault.py`에
`compact_for_embedding()`(표는 헤더+샘플 5행만 남기고 잘라냄)을 추가해 즉시 배포 →
표 있는 문서 대부분의 `content_hash`가 바뀌어 이미 몇 시간째 돌던 25만~250만 건
규모 임베딩 작업 대부분이 재작업 대상이 됨. **고친 것 자체는 맞는 방향**(기존
임베딩이 실제로 검색 순위를 잘못 매기고 있었으니 재작업이 필요한 게 맞음)이었지만,
배포 전에 거쳐야 했던 단계를 건너뛰어 대응이 늦었고 사용자가 뒤늦게 "왜 재작업이
필요한지" 직접 물어야 했음.

**재발 방지 체크리스트** — 이미 대량으로 돌고 있는(또는 곧 대량으로 돌릴) 파이프라인의
전처리/파싱 로직을 바꿀 때는 아래 순서를 반드시 지킬 것:
1. **작게 먼저 검증**: 실제로 문제가 재현된 정확한 사례(이번엔 Rembrandt 검색)로
   "고친 함수의 출력이 달라졌다"뿐 아니라 "그래서 실제 증상(검색 순위)이 고쳐졌는지"
   까지 소규모로 먼저 확인. 이번엔 `compact_for_embedding()` 출력 길이만 확인하고
   바로 전체 재시작해버려서, 재임베딩 완료 후에야 진짜 고쳐졌는지 알 수 있었음.
2. **영향 범위 먼저 추정**: `content_hash` 계산 로직을 바꾸면 기존 저장된 해시가
   전부 무효화된다 — 배포 전에 "이 변경으로 몇 건이 재작업 대상이 되는지"를 SQL로
   미리 추정(예: 표가 5행 넘는 문서 수 카운트)하고, 그 비용(몇 시간 vs 며칠)을
   사용자에게 먼저 알리고 진행할지 판단받는 게 나음 — 특히 이미 몇 시간 이상 돌고
   있는 작업일수록 "지금 당장 반영 vs 이번 배치 완주 후 반영"을 저울질해야 함.
3. **여러 세션이 같은 파이프라인을 동시에 돌릴 때 코드 변경은 핫배포 위험**: 이번엔
   메인이 코드를 고치고 자기 프로세스만 먼저 재시작한 뒤 워커2에게 뒤늦게 알렸음 —
   그 사이 워커2는 구버전 코드로 계속 쓰고 있었을 수 있음(다행히 워커2가 자기
   프로세스가 무응답으로 죽어있던 걸 발견해 재시작하면서 자연히 최신 코드로
   맞춰졌지만, 우연에 기댄 것). 앞으로는 파이프라인 코드를 바꾸면 **관련된 모든
   세션에 동시에 알리고, 전부 재시작 확인될 때까지 "일부는 구버전, 일부는 신버전"
   상태로 방치하지 않을 것**.

## 4. 애매하면: 기록하고 다음으로, 판단은 사용자 몫으로 남긴다

이 기준의 목적은 "판단을 대신 내리는 것"이 아니라 "판단이 필요 없는 일은
안 멈추고 계속하는 것"이다. 애매한 판단(법적/윤리적 회색지대, 스코프 확장
여부, 대규모 자동 병합)은 자율 루프 중에도 항상 문서에 기록해 사용자가
복귀했을 때 바로 결정할 수 있게 남겨두고, 그 사이엔 막힌 항목을 스킵하고
계속 진행한다 — 판단 대기가 곧 전체 정지로 이어지면 안 된다.
