## 진단 — Wikidata 사건 잡이 느린 원인

`crawlers/wikidata_artist_events.py` 92~93행:
```python
for bi, b in enumerate(batches[...]):
    key = f"b{bi:04d}_" + hashlib.md5(",".join(b).encode()).hexdigest()[:8]
    if already_fetched(SITE_NAME, key): ...
```
QID 목록을 `order by 1`(문자열 정렬, 숫자 정렬 아님 — "Q123"과 "Q45"의 사전식 비교)로 가져와 200개씩 **위치
기준**으로 자른 뒤, 배치 인덱스(`bi`)와 그 배치 내용의 해시를 키로 쓴다. 문제는 M6-c·`backfill_artist_meta_
wikidata.py` 등으로 **artists.wikidata_qid가 계속 늘어나는 중**이라는 점 — 새 QID가 중간 어딘가에 끼어들면
그 뒤 모든 배치의 "200개 묶음"이 한 칸씩 밀리고, 배치 인덱스는 같아도 내용물이 달라져 해시가 바뀐다.
**결과: QID가 조금만 늘어도 그 지점 이후 배치가 전부 "새 배치"로 오인돼 재수집된다** — 이게 이번 실행이
161배치 중 상당수를 다시 돌리며 20분 넘게 걸리는 원인으로 확인됨(오늘 아침 M6 계열 백필로 QID가 늘어난
상태에서 재실행했기 때문). 개별 배치의 SPARQL 자체도 가볍지 않음(`Q_EXH`가 `wdt:P279*`로 전이적 폐포를
계산 + `SERVICE wikibase:label`을 매 배치 실행) — 배치당 1.2+1.2초 sleep 외에도 쿼리 자체가 수 초씩 걸릴 수
있어 "재수집 안 해도 되는" 상황에서도 배치당 비용이 낮지 않다.

**결론**: 이 잡은 QID 집합이 고정이면(더 이상 안 늘어나면) idempotent하지만, 지금처럼 다른 작업(M6 백필)이
계속 QID를 늘리는 동안은 **매번 대량 재수집이 발생해 "가벼운 증분 잡"이 아니라 "거의 매번 풀스캔"**이 된다.

## 재설계 완료 (2026-09-17, 메인 승인)

배치 키를 위치 인덱스에서 **QID 자체**로 바꿨다 — `crawlers/raw/wikidata_artist_events/<QID>.json` 1개당
1파일(SPARQL 조회는 여전히 200개씩 묶어 보내되, 응답을 QID별로 쪼개 저장). 사건 0건인 QID도 빈 결과로
저장해 재조회 방지. `--refresh-days N` 옵션 추가(N일 지난 QID는 사건 갱신을 위해 재조회, 기본은 신규
QID만). 로더(`pipeline/wikidata_artist_events.py`)는 파일 단위로 glob해 이벤트를 모으는 방식이라 배치
크기와 무관하게 그대로 동작 — 예전 배치 파일(`b0000_*.json` 등)도 삭제하지 않고 같이 읽힘, 코드 수정
불필요했음. 부수 결함 발견·수정: `sources` 테이블 insert가 매번 새 raw_path로 시도해 재실행 시 유니크
제약 위반으로 죽었음 — `on conflict (raw_path) do update`로 변경.

**검증**: 1차 실행(마이그레이션, 전체 QID 35,578개 대상) 18분30초 소요, 178 SPARQL 배치. `--apply` 결과
award 236·death 2,851(death_year 신규 192)·exhibition 1,685·exhibition_artist 1,802 반영. **2차 실행(같은
QID 집합) 3.5초, 대상 0개**(전부 신선함으로 스킵) — 2차 `--apply`도 신규 0건(idempotent, 중복 없음). 이제
정말로 "가벼운 증분 잡"이 됐다.

## 갤러리 5곳 적재 검증 (메인 확인 요청, 2026-09-17)

```python
def match_artist(name: str, artists_by_name: dict) -> str | None:
    return artists_by_name.get(name.strip().lower())
```
`artists_by_name`은 `load_lookup()`(71~82행)이 `artists.name`/`artists.name_en`을 소문자로 미리 채운 dict —

## 발견사항 — K-ARTMARKET 크롤러의 구조적 한계

`kams_stats.py`는 `already_fetched(SITE_NAME, RECORD_ID)`를 단일 고정 `RECORD_ID`로 검사한다(스크립트 22·39행).
즉 **페이지 자체가 언제 갱신되든 최초 1회 저장 이후 절대 재수집되지 않는다** — 다른 크롤러들(Bonhams/Wikidata)이
개별 항목(세일 ID, statement GUID) 단위로 already_fetched를 거는 것과 다른 설계다. K-ARTMARKET
"미술시장 실태조사"는 연 1회(보통 다음해 상반기) 전년도 행이 추가되는 방식이라, 지금 구조로는 **매년 새 연도
데이터가 나와도 자동으로는 절대 못 잡는다**. 로드맵 7(자동 갱신)에 이 잡을 포함하려면 코드 수정
(RECORD_ID에 연도 또는 컨텐츠 해시를 넣어 재수집 트리거) 이 선행돼야 함 — 이번엔 리포트만, 코드 수정은
안 함(범위 밖).

## refresh_weekly.ps1 통합 스크립트 (2026-09-17, 메인 지시)

5개 잡(Bonhams/Wikidata경매/K-ARTMARKET/Wikidata사건/갤러리5곳)을 `pipeline/refresh_weekly.ps1`로
순차 실행하도록 묶었다. 각 단계는 독립 실패해도 다음 단계로 계속 진행, 로그는
`docs/logs/refresh_YYYYMMDD.log`. 개발 중 발견한 함정 2건, 재발 방지로 스크립트에 반영:
1. `pipeline/run.py`는 `os.environ["DATABASE_URL"]`만 직접 확인하고 `.env` 폴백이 없어서
   PowerShell에서 그냥 실행하면 조용히 dry-run으로 빠진다 — 스크립트 상단에서 `pipeline/.env`를
   읽어 프로세스 환경변수로 주입하도록 추가(하드코딩 아님, 파일에서만 읽음).
2. PowerShell 5.1의 `Tee-Object`에는 `-Encoding` 파라미터가 없다(PS7+ 전용) — 처음에 이걸 몰라서
   전체 실행이 즉시 실패했다가(1차 시도), 캡처 후 `Write-Host`+`Out-File -Encoding utf8`로 나눠
   고쳤다. **알려진 잔여 결함**: 이렇게 고친 뒤에도 로그 파일의 "===== [시각] 단계명 시작/종료 ====="
   구분선만 한글이 깨져서 저장됨(`Add-Content -Encoding utf8`을 썼는데도 발생, 원인 미확인) —
   단계별 실제 명령 출력(수치·리포트 등 실질 내용)은 정상 UTF-8로 읽힌다. 기능에는 영향 없어
   이번엔 더 안 고치고 기록만 남김.

**검증**: 3회 연속 실행(1차 DB반영 없이 dry-run 버그 발견 → 2차 DB반영 확인+Tee-Object 버그로 즉시
실패 → 3차 전체 정상, exit 0 전 단계) — 3차 실행 결과 전부 idempotent(신규 0건), Bonhams
크롤 8초+로더 65초, Wikidata경매 크롤 18초+로더 18초, K-ARTMARKET 크롤 2초+로더 3초, Wikidata사건
크롤+로더 합계 106초(QID 소량 신규분 처리, 완전 무변화 시 3~4초와 별개), 갤러리 5곳 크롤 3초+로더
4초. **전체 소요 약 3분 20초**(2026-09-17 10:02:25~10:06:32).

## 종합 판단 (로드맵 7 착수 자료)

- Bonhams·Wikidata 경매는 **이미 "재실행 가능한 갱신 잡"으로 완성 상태** — 스케줄러(cron 등)에 그대로 얹어도
  안전. 소요도 가볍다(각 1분 내외).
- K-ARTMARKET은 **현재 코드로는 갱신 잡이 아니라 "최초 1회용" 스크립트**다. 로드맵 7 착수 전 위 구조적 한계를
  고쳐야 한다.
- Wikidata 사건은 배치 경계 시프트 문제 때문에 "부분 재수집"이 발생할 수 있어 완전한 idempotent라고 단정하기
  어려움 — 실측 결과로 아래 갱신.
