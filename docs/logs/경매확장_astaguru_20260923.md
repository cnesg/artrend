  걸렸는데, 확인 결과 **대문자 경로를 쓰던 구(舊) ASP.NET 사이트의 잔재**다
  (같은 목록의 `/default.aspx` `/Online_Auction.aspx` `/Home/` 도 같은 세대의 잔재).
  현행 과거 낙찰 결과는 Next.js 사이트의 `/auctions/results/<year>/<slug>-<id>`로
  서비스되고 sitemap.xml에도 그 경로로 올라와 있다(`/auctions/results/2025/
  Imperial-Treasures-200` 등 42건). robots.txt 경로 매칭은 대소문자를 구분하므로
  `/Past/`가 `/auctions/results/`를 덮지 않는다. **그래도 확실히 하려고 `/Past/`
  경로는 아예 한 번도 요청하지 않았다.**
- 이 크롤러가 실제로 쓰는 `/api/auctions/*`에도 제한이 없다.
- Disallow된 `/department/*` 4개(희귀서적·만년필·인도골동·자연사)는 애초에 이
  프로젝트 스코프(미술품) 밖이라 무관하다.

## 2. 이용약관 전문 확인 — 4개 문서, 금지 조항 전혀 없음

실제 GET으로 받아 script/style/태그를 제거한 순수 텍스트에서 다음 키워드를 전수 검색:
`crawl|scrap|spider|robot|data ?min|text and data|harvest|automated|bot|extract|
index|reproduc|database right|sui generis|personal use|non-commercial|third part|
redistribut|intellectual propert|copyright|download|retriev|aggregat|monitor`

| 문서 | URL | 순수 텍스트 길이 | 결과 |
|---|---|---|---|
| Terms and Conditions **of Sale** | `/terms-and-conditions` | 44,495자 | 금지 조항 검출 없음 |
| Privacy Policy | `/privacy-policy` | 22,363자 | 금지 조항 검출 없음 |
| Cookie Policy | `/cookie-policy` | 5,761자 | 검출 없음 |
| FAQs | `/faqs` | 5,368자 | 검출 없음 |

핵심 소견:

- **`crawl`/`scrape`/`spider`/`robot`/`data mining`/`database right`/`sui generis`는
  4개 문서 어디에도 단 한 번도 나오지 않는다.**
- `/terms-and-conditions`는 제목 그대로 **"Terms and Conditions of *Sale*"**이다.
  1 정의 → 2 등록 → 3~4 입찰 → 5 진품성 → 6 결제 → 7 배송 → 8~9 책임범위 →
  10~11 상태고지 → 12 기타 구성으로, **응찰자/낙찰자의 매매상 의무만** 다루고
  **웹사이트 이용(acceptable use) 조항 자체가 존재하지 않는다**. 페이지 상단의
  "Astaguru (T&C) / UK (T&C) / Singapore (T&C)" 탭도 같은 매매약관의 관할별
  변형이다(같은 페이지에 `DEFINITIONS AND INTERPRETATION`이 2회 등장).
- 검색에 걸린 `extract`는 시계 부속 서류(11.4.2 "Certificates/papers/cards/
  **extracts** are not available…"), `copyright`는 낙찰 후 저작권 양도 시점
  (6.1)과 푸터 표기뿐 — 데이터 이용과 무관하다.
- `privacy-policy`는 응찰자 개인정보 처리 고지이고 공개 카탈로그 데이터 이용을
  제한하지 않는다.
- 푸터에 "Seller Terms" / "Store Terms" 문구가 있으나 **링크가 걸려 있지 않은
  비활성 텍스트**(`<div class="hidden">` 안의 `<h4>`)다 — 별도 문서가 공개돼 있지 않다.

## 3. 구조 — 화면은 CSR이지만 인증 불필요 공개 JSON API 두 개로 전부 나온다

`/auctions/results/<year>/<slug>-<id>` HTML은 Next.js CSR이라 **본문에 로트가 없다**
(태그 제거 후 866자뿐 — 내비게이션과 푸터만). 브라우저로 열어 네트워크를 관찰해
페이지가 호출하는 내부 API 두 개를 찾았다. **쿠키·토큰·로그인 전부 불필요**:

| 용도 | 엔드포인트 |
|---|---|
| 과거 세일 목록 | `/api/auctions/get-auctions-by-status?auctionType=PAST&sortOrder=desc&limit=300` |
| 세일별 로트 | `/api/auctions/filter-lots?auctionId=<id>&limit=<n>&page=<n>` |

로트 하나가 주는 필드(발췌): `lotID`, `productID`, `creatorValue`(작가명),
`creatorID`(AstaGuru 내부 GUID), `title`, `creationYearValue`, `mediumValue`,
`size`, `description`(카탈로그 원문), `provenance`, `category`,
`priceMinINR`/`priceMaxINR`(추정가), `auctionState.currentHammerINR`(낙찰가),
`auctionState.totalBidCount`.

### 3-1. **과거 세일의 filter-lots는 낙찰된 로트만 돌려준다 — 수치로 검증함**

유찰 로트가 섞여 있는지 확인하려고, 세일별 `sum(currentHammerINR)`에 낙찰수수료를
곱한 값이 사이트가 공시하는 Total Sale과 맞는지 **133개 세일 전수 대조**했다:

- 2026-08 Iconic Masters: 974,130,119 × 1.21 = **1,178,697,444** (공시값과 정확히 일치)
- 2026-09 Imperial Treasures: 25,078,980 × 1.21 = **30,345,566** (정확히 일치)
- **133개 중 132개가 프리미엄 배수(시기별 1.18 또는 1.21)로 정확히 일치**. 유일한
  예외는 2008년 첫 세일(비율 1.10 — 프리미엄 10% 시절) 하나이고 이것도 합계는 맞는다.

→ 유찰 로트는 애초에 응답에 없다. 따라서 로더는 전부 `sold=True`,
`hammer_price = currentHammerINR`로 적재한다. **페이지네이션 누락도 이 대조로 동시에
배제됐다**(일부만 받았다면 합계가 맞을 수 없다).

### 3-2. 함정 — **`creatorType` 필드를 작가 판정에 쓰면 안 된다**

처음엔 `creatorType == 'Artist'`로 미술품을 걸렀다. 연도별 집계를 보다가 **2025년이
615건 → 184건으로 줄어드는 것**을 발견해 파고든 결과, `creatorType`이 값이
`'Artist'`/`'Brand'`/빈 문자열로 **일관되게 채워져 있지 않다**는 걸 확인했다.
미술 전문 세일인데도 전 로트가 `creatorType: ""`인 세일이 여럿이다:

## 4. 개인정보 — 응답에 섞인 식별자는 저장 전에 제거

`filter-lots` 응답에는 로트 사실 데이터 외에 **낙찰자/최고응찰자의 Firebase UID**
(`winnerClientID`, `leadingClientID`, `outbidClientID`)와 위탁자 필드
(`consignerID`, `consignerName`, `crID`, `crName`, `sourcingCrID`, `sourcingCrName`)가
들어 있다. 이 프로젝트가 필요로 하는 건 작가·작품·추정가·낙찰가뿐이라
**크롤러가 raw 저장 전에 해당 키만 제거**한다(`crawlers/astaguru.py`의 `_strip_pii`).
"크롤러는 원본만 저장한다"는 관례의 의도적 예외이며 코드 독스트링과 meta의
`license_note`에도 남겼다.

**위탁자 필드 6개가 혹시 작가명을 담고 있어 정보를 잃는 건 아닌지** 라이브 API로
별도 검증했다 — 연도를 흩어 고른 14개 세일 **1,557 로트 전수 확인 결과 6개 필드 모두
100% 빈 문자열**이었다. 작가명은 오직 `creatorValue`에만 들어 있다. 카탈로그 원문인
`provenance`("Property from a Parsi collection based in Mumbai" 같은 이미 익명화된
공개 문구)는 그대로 둔다. 이미지 파일도 저장하지 않는다(URL 문자열만 남음).

## 6. 남은 과제

1. **주간 자동갱신 연결(로드맵 7)** — 이 소스는 증분이 아주 싸다.
   `crawlers/astaguru.py --phase auctions` 1회(세일 목록 갱신) +
   `--phase lots --since-id <마지막 적재 id>` 로 신규 세일만 받고
   `pipeline/_scratch/load_astaguru_20260923.py`를 다시 돌리면 끝난다
   (`already_fetched` + `sources.raw_path`로 양쪽 다 idempotent). 월 1~2회 새 세일이
   열리므로 `refresh_weekly.ps1`에 붙이기 적합하다. **이번 세션에서는 다른 세션이
   같은 파일을 편집 중일 수 있어 `refresh_weekly.ps1`을 건드리지 않았다.**
2. **`price_usd` 미채움** — 응답에 USD/GBP/SGD 환산값이 있지만 **낙찰 시점 환율이
   아니라 조회 시점 환율**이다(`currencies[].conversionRate`가 요청할 때마다 현재
   환율로 들어온다). 과거 낙찰가에 현재 환율을 곱한 값은 이 프로젝트가 이미
   "임의 환율 시장지표"로 폐기한 것과 같은 종류의 오염이라 **일부러 비워 뒀다**.
   `auction_lots.currency = 'INR'`로만 들어가 있고, USD 정규화가 필요해지면 역사
   환율 테이블을 따로 붙이는 게 맞다.
3. **`provenance` 필드 미활용** — 응답에 로트별 provenance 원문이 있다.
   `provenance_extract.py` 같은 후처리로 `provenance_records`/`collectors`를 채울
   여지가 있으나 이번 착수 범위 밖으로 남긴다.
4. **미술 외 카테고리 2,686건** — 보석·시계·은제품·클래식카 등. 프로젝트 스코프
   밖이라 의도적으로 버렸다(재수집 없이 raw에 그대로 남아 있으니 스코프가 바뀌면
   로더만 고쳐 적재 가능).
5. **Saffronart이 실제로는 적재돼 있지 않다 — AstaGuru가 인도 첫 소스다.**
   이번 착수는 "Saffronart(인도)는 이미 수집됨"을 전제로 시작했는데, 확인 결과
   그렇지 않다:
   - `auction_houses`를 `%saffron%` `%pundole%` `%india%` `%mumbai%` `%bombay%`로
     조회 → **전부 0건**(`%astaguru%`만 이번에 생긴 1건).
   - `sources.site_name` 전체 목록(230여 개)에도 `saffronart`류가 **없다**.

   즉 이 적재 이전까지 인도 경매 소스는 DB에 **하나도 없었고**, AstaGuru가 첫
   인도 소스다. Saffronart 착수 여부는 별도 조사 대상으로 남긴다(이 세션 범위 밖).

## 7. 사고 메모 — pgportable 다운

검증 쿼리 하나(`museum_holdings`에 상관 서브쿼리 `IN (select … where artist_id = g.artist_id)`를
건 조인)를 돌리다 **DB가 죽었다**. 로그상 `백그라운드 작업자 "parallel worker" …
0xC000013A 예외로 인해 종료됨` → 전체 재초기화. 이 프로젝트가 이미 기록해 둔
pgportable 불안정 패턴과 같은 모양이다.

- **적재분은 무사했다** — 로더가 배치마다 커밋하는 구조라 7,181건 전부 보존됐고,
  재기동 후 재검증에서 동일한 수치가 나왔다.
- 복구: `Start-Process C:\pgportable\pgsql\bin\postgres.exe -ArgumentList "-D","C:\pgportable\data","-p","5433"`
  (죽은 뒤 postmaster가 "재 초기화 중"에서 멈춰 있었고 5433 리슨이 없어 수동 재기동함).
- 교훈: 검증 쿼리도 상관 서브쿼리 대신 **임시 테이블 + 인덱스 + `statement_timeout`**으로
  짜야 한다(고쳐서 다시 돌렸을 때는 문제없이 완료).
